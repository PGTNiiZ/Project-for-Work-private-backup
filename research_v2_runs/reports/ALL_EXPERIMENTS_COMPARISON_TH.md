## 1. บทนำ: โครงการพยายามทำอะไร และทำไมต้องรวบรวมครั้งนี้

โครงการนี้ต้องการตัดสินว่าโปรไฟล์โซเชียลมีเดียสองอันจากต่างแพลตฟอร์ม (Twitter, Google+, Instagram) เป็นของคนเดียวกันหรือไม่
ข้อมูลหลักมีโปรไฟล์ 36,807 แถว ซึ่งใช้ได้ 36,804 แถว และมีคู่ที่เป็นคนเดียวกันจริงข้ามแพลตฟอร์ม 29,243 คู่
"คนเดียวกันจริง" ในโครงการนี้หมายถึงโปรไฟล์ที่อยู่ในโฟลเดอร์ผู้ใช้ (`user_folder`) เดียวกันในชุดข้อมูลต้นทาง
ซึ่งเป็นสมมติฐานเชิงปฏิบัติการ ยังไม่มีใครตรวจด้วยคน (`research_v2_runs/metrics/label_sanity.json`, `research_v2_runs/DEVIATIONS.md`)

ระบบทุกรุ่นมีโครงเดียวกัน 4–5 ขั้น:

```
โปรไฟล์ → [1 คัดคู่ผู้สมัคร] → [2 แปลงคู่เป็นตัวเลข] → [3 โมเดลให้คะแนน] → [4 ปรับคะแนนเป็นความน่าจะเป็น] → [5 กฎตัดสินใจ]
           blocking             features                  model               calibration                     decision policy
```

- **คัดคู่ผู้สมัคร (blocking)** เลือกเฉพาะคู่ที่ดูคล้ายกันมาพิจารณาต่อ เพราะเทียบทุกคู่ไม่ไหว (ทั้งคลังมีคู่ข้ามแพลตฟอร์ม 449,149,239 คู่)
  ตัววัดคือ **PC (pair completeness)** = สัดส่วนคู่จริงที่ยังอยู่ในรายการ เช่น คู่จริง 100 คู่ อยู่ในรายการ 92 คู่ → PC 0.92
- **feature** คือตัวเลขที่อธิบายคู่หนึ่งคู่ เช่น "ชื่อผู้ใช้คล้ายกัน 0.93"
- **โมเดล** ให้คะแนนคู่ คุณภาพการจัดอันดับวัดด้วย **AP (average precision)** ค่า 0–1 ยิ่งสูงยิ่งดี
  ข้อควรระวัง: AP ขึ้นกับสัดส่วนคู่จริงในชุดที่วัดมาก ชุดที่มีคู่จริงครึ่งหนึ่งจะได้ AP สูงกว่าชุดที่มีคู่จริง 3% แม้จะใช้โมเดลเดียวกัน
- **calibration** แปลงคะแนนเป็นความน่าจะเป็น เช่น isotonic (ฟิตเป็นขั้นบันได) หรือ Platt (ฟิตเป็นเส้นโค้งรูปตัว S)
- **กฎตัดสินใจ** แบ่งคู่เป็น "รวมอัตโนมัติ (MATCH) / ส่งคนตรวจ (REVIEW) / ไม่รวม (NO_MATCH)"

**ทำไมต้องรวบรวม:** โครงการมีการทดลองหลายสิบชุดตลอด 10 เดือน แต่ละชุดวัดด้วยนิยามต่างกัน โดยเฉพาะ **ตัวหารของ recall**
(recall = สัดส่วนคู่จริงที่ระบบจับได้) บางชุดหารด้วยคู่จริงในชุดตัวอย่างที่สุ่มมา บางชุดหารด้วยคู่จริงทั้งหมดรวมคู่ที่หลุดตอนคัดคู่
ตัวเลขเช่น "F1 0.934" กับ "F1 0.861" จึงอาจไม่ได้วัดสิ่งเดียวกันเลย เอกสารนี้แยกให้เห็นว่าตัวเลขไหนเทียบกันได้ และตัวเลขไหนห้ามเทียบ

*แหล่งที่มา: `research_v2_runs/metrics/label_sanity.json`, `pub_multi/ref/full_report.json` (`data_report`), `research_v2_runs/DEVIATIONS.md`*

(ต่อไปเรียกว่า "เอกสารตรวจย้อนหลัง") เป็นแผนที่ แล้วเปิดไฟล์ผลจริงในเครื่องเพื่อยืนยันตัวเลขทุกตัวที่ทำได้

คำอธิบายช่องข้อมูลที่ใช้ด้านล่าง:
- **ประเภทการประเมิน**: *ชุดทดสอบปิดผนึก* (ข้อมูลที่ไม่ได้ใช้เลือกอะไร), *นอก fold ของข้อมูลพัฒนา* (OOF: คะแนนจากโมเดลที่ไม่เคยเห็น fold นั้น แต่ข้อมูลเดียวกันถูกใช้เลือกค่าตั้งซ้ำ),
  *ชุดทดสอบที่ถูกใช้ซ้ำ* (มีชุดทดสอบแยกแต่ถูกเปิดดูหลายครั้ง), *notebook ไม่มีการแบ่งชัด*, *ทั้งคลัง* (ไม่มีชุดแยก)
- **entity-disjoint** = คนคนเดียวกันอยู่ฝั่งเดียว (ฝึกหรือสอบ) ไม่ข้ามกัน ป้องกันโมเดล "จำคน"

## 7. ผลที่ดีที่สุดที่รู้ แยกตามขั้นของระบบ

**ทำไมต้องแยกตามขั้น:** ระบบมีหลายขั้น และ "ดีที่สุด" ของขั้นหนึ่งวัดคนละแบบกับอีกขั้น

**ขั้นคัดคู่.** ผลที่เชื่อถือได้ที่สุดคือ **sparse PC 0.9245 บนชุดสอบปิดผนึก** (งบ 87,702 คู่) ซึ่งดีกว่า B0 (0.8870) และเทียบเท่า hybrid RRF (0.9241)
ผลที่สูงกว่านั้นคือหลายเส้นทาง post-hoc PC 0.9345 (1×) / 0.9376 (2×) บนข้อมูลพัฒนา แต่เป็น post-hoc และยังไม่มีผลบนชุดสอบ
dense/hash blocking ล้มเหลวทั้งใน V2 (PC 0.6028) และชุด R (R6 กู้ได้ 4/3,316) — สองข้อนี้สอดคล้องกันในทิศทาง แม้วัดคนละแบบ
*ความเชื่อถือ:* ปานกลาง (test exploratory) สำหรับ sparse; ต่ำสำหรับหลายเส้นทาง

**ขั้น feature.** บนชุดสอบ V2 feature ข้อความ 35 ตัว ดีกว่ากลุ่มเดียวที่ดีที่สุดอย่างชัดเจน (H1) และการเพิ่ม feature ความหมายไม่ช่วย (H3 เทียบเท่า)
ชื่อเต็มเป็นสัญญาณที่สำคัญที่สุด (ตัดออกแล้ว AP dev ตกจาก 0.9778 เป็น 0.9128) ส่วนที่อยู่แทบไม่มีผล ข้อหลังนี้สอดคล้องกับ bigram (#2) และ post-hoc (#43)
feature รูปภาพเพิ่ม AP ได้เพียง 0.0007 ในวิทยานิพนธ์ (G9) และไม่เคยถูกทดสอบในรอบที่สะอาด
post-hoc ชี้ว่าการรวม feature งานก่อน (โดยเฉพาะจำนวนโดเมนในลิงก์) อาจช่วย แต่ยังไม่ผ่านชุดสอบ
*ความเชื่อถือ:* ปานกลางสำหรับ H1/H3; ต่ำสำหรับรูปภาพและชุดรวม

**ขั้นโมเดล.** GBDT ดีกว่า LR และกฎในทุกรอบที่วัด (V2 G3/G5, วิทยานิพนธ์ G9b, คลาสสิก G10) ผลที่เชื่อถือได้ที่สุด: GBDT feature ข้อความ AP 0.9790 บนชุดสอบ V2 (H2 Δ 0.0553 เทียบกฎ)
*ความเชื่อถือ:* ปานกลาง และทิศทางเดียวกันทุกยุค

**ขั้น calibration.** V2 เลือก Platt บนข้อมูลพัฒนา (Brier ลดจาก 0.0083 เมื่อไม่ปรับ เป็น 0.0049 เมื่อใช้ Platt) โดยการเลือกใช้ข้อมูลเดียวกันซ้ำ
ICSEC v2 พบปัญหาสัดส่วนคู่จริงต่างกันระหว่างชุด calibration (5.7%) กับชุดสอบ (2.2%) ตามเอกสารตรวจย้อนหลัง (UNVERIFIED ในเครื่องนี้)
post-hoc นำ Platt ของ V2 ไปใช้กับโมเดลใหม่โดยไม่ฟิตใหม่ ตัวเลข recall/precision ของ post-hoc จึงอาจเพี้ยน
*ความเชื่อถือ:* ต่ำ — ไม่มีการพิสูจน์ calibration บนประชากรอื่นเลย

**ขั้นกฎตัดสินใจ.** บนชุดสอบ V2 กฎสามทางให้ต้นทุนต่ำสุด (4.48×10⁻⁵/คู่) และ GA **ไม่** ดีกว่า Chow หรือตัวค้นหาอื่นที่งบเท่ากัน (H4 ไม่สนับสนุน)
สอดคล้องกับ ICSEC v2 ที่ B2 (Sobol) ≈ B3 (GA) และประโยชน์มาจากการจูนบน validation (B0 → B1) และกับ #21 ที่ GA 10 ยีนแทบไม่ต่างจากกฎสองเกณฑ์
*ความเชื่อถือ:* ปานกลาง และสอดคล้องกันสามแหล่ง; แต่ต้นทุน 2:1:0.1 เป็นสมมติฐาน ไม่ได้วัดจากธุรกิจจริง

## 11. อภิธานศัพท์ และตารางจับคู่ชื่อ

### 11.1 อภิธานศัพท์

- **คัดคู่ผู้สมัคร (blocking)** — เลือกเฉพาะคู่ที่น่าจะเป็นคนเดียวกันมาพิจารณาต่อ เช่น คู่ที่ 3 ตัวอักษรแรกของชื่อผู้ใช้ตรงกัน
- **งบ (budget)** — จำนวนคู่ผู้สมัครที่ยอมให้มี
- **PC (pair completeness)** — สัดส่วนคู่จริงที่อยู่ในรายการคู่ผู้สมัคร
- **exact tier** — คู่ที่ชื่อผู้ใช้หรือ URL ตรงกันพอดี ถูกรวมอัตโนมัติโดยไม่ผ่านโมเดล
- **feature** — ตัวเลขที่อธิบายคู่ เช่น ความคล้ายของชื่อ 0.93
- **AP (average precision)** — คุณภาพการจัดอันดับ 0–1 ขึ้นกับสัดส่วนคู่จริงในชุดที่วัดมาก
- **AUC** — โอกาสที่คู่จริงสุ่มหนึ่งคู่ได้คะแนนสูงกว่าคู่ไม่จริงสุ่มหนึ่งคู่
- **precision** — ในคู่ที่ระบบรวม มีกี่ส่วนที่ถูก
- **recall** — ในคู่จริง ระบบจับได้กี่ส่วน: *บนคู่ผู้สมัคร* หารด้วยคู่จริงในรายการ; *ทั้งระบบ (end-to-end)* หารด้วยคู่จริงทั้งหมดรวมคู่ที่หลุด;
  *decision recall* (ICSEC v2) ไม่นับคู่จริงที่ถูกส่งตรวจในตัวหาร
- **F1** — ค่าเฉลี่ยแบบ harmonic ของ precision กับ recall ต้องรู้ว่าใช้ recall แบบไหน
- **REVIEW / MATCH / NO_MATCH** — ส่งคนตรวจ / รวมอัตโนมัติ / ไม่รวม
- **calibration (isotonic, Platt)** — แปลงคะแนนเป็นความน่าจะเป็น; isotonic เป็นขั้นบันได, Platt เป็นเส้นโค้งตัว S
- **ECE / Brier** — ตัววัดว่าความน่าจะเป็นตรงกับสัดส่วนจริงแค่ไหน ยิ่งต่ำยิ่งดี
- **กฎ Chow** — เลือกการกระทำที่ต้นทุนคาดหวังต่ำสุด ที่ต้นทุน 2:1:0.1 คือรวมเมื่อ p > 0.95 ส่งตรวจเมื่อ 0.1–0.95
- **ต้นทุน / U** — ผลรวมถ่วงน้ำหนักของรวมผิด พลาด และส่งตรวจ เช่น 2×รวมผิด + 1×พลาด + 0.1×ส่งตรวจ (น้ำหนักเป็นสมมติฐาน)
- **GA (genetic algorithm)** — ค้นค่าตั้งแบบวิวัฒนาการ
- **Sobol / random / TPE** — วิธีค้นค่าตั้งอื่น: กระจายสม่ำเสมอ / สุ่ม / เรียนจากรอบก่อน
- **GBDT / GB** — ต้นไม้ตัดสินใจหลายต้นต่อกัน; **LR** — logistic regression เส้นตรง; **RF** — ต้นไม้หลายต้นแบบสุ่ม; **MLP / IdentityMLP** — โครงข่ายประสาทหลายชั้น
- **MiniLM / SBERT / MPNet / DistilBERT** — โมเดลภาษาที่แปลงข้อความเป็นเวกเตอร์ความหมาย
- **Bloom filter** — เข้ารหัสข้อความเป็นบิตเพื่อซ่อนชื่อจริง L คือความยาวบิต
- **entity-disjoint** — คนคนเดียวกันไม่อยู่ทั้งฝั่งฝึกและฝั่งสอบ
- **fold / cross-validation / OOF** — แบ่งข้อมูลหลายส่วน ผลัดกันสอบ; คะแนนนอก fold คือคะแนนจากโมเดลที่ไม่เคยเห็น fold นั้น
- **การแบ่งซ้อน (nested split)** — แบ่งข้อมูลพัฒนาต่อเป็นส่วนฝึก/calibration/จูนกฎ เพื่อไม่ให้จูนบนคู่ที่ใช้ฝึก
- **ชุดทดสอบปิดผนึก (sealed test)** — ข้อมูลที่ไม่ได้ใช้เลือกอะไรเลยจนกว่าทุกค่าจะถูกตรึง
- **ชุดทดสอบที่ถูกใช้ซ้ำ** — ชุดสอบที่ถูกดูผลหลายครั้ง ทำให้การเลือกในรอบหลังอาจโน้มเอียงตามมัน
- **confirmatory / exploratory / post-hoc** — ยืนยันสมมติฐานที่ลงทะเบียนล่วงหน้าบนข้อมูลสะอาด / สำรวจ / ทำหลังเห็นผล
- **bootstrap / CI / Holm / TOST** — สุ่มซ้ำเพื่อประมาณความไม่แน่นอน / ช่วงความเชื่อมั่น / ปรับค่า p เมื่อทดสอบหลายข้อ / ทดสอบความเทียบเท่า
- **seed** — ตัวเลขตั้งต้นของการสุ่ม; SD ข้าม seed วัดความแปรปรวนจากการสุ่มเท่านั้น
- **prior** — สัดส่วนคู่จริงในประชากร (เช่น 53% ในชุดสุ่มของวิทยานิพนธ์ vs 0.66% ในคู่ผู้สมัครทั้งคลัง)
- **LFS** — ระบบเก็บไฟล์ใหญ่ของ git ที่เก็บ pointer แทนเนื้อหา
- **G0, G1, G5** — เกณฑ์ผ่านของโครงการ V2; G0/G1 ผู้วิจัยประกาศว่าผ่านโดยไม่มีเอกสารอ้างอิง, G5 (ข้อมูลไม่เคยถูกใช้มาก่อน) ไม่ผ่าน
- **H1–H5** — สมมติฐานหลัก 5 ข้อของ Research V2 (ดูหัวข้อ 5.1)
