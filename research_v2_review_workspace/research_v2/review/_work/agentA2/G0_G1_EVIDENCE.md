## G0 — Where `user_folder` ground truth came from

### What exists

1. **Mechanism by which the project obtains `user_folder`.** It is the name of the per-user directory in the upstream raw dataset. `load_all_profiles` iterates `{1,2,3}.profile.data/<user_folder>/*.json`, sets `data['user_folder'] = user_folder`, and infers platform from the JSON file name [BK1:src/identity_resolution/stages/prepare.py#L28-L69 load_all_profiles]. The project therefore **inherits** the entity grouping from the upstream folder layout and did not create it. No project code assigns or edits entity membership. Missing values are filled with a singleton id [BK1:src/identity_resolution/stages/pairs.py#L490].
2. **Upstream source named as LinkSocial.** The local input is "a transformed derivative of the public LinkSocial repository (Dataset-LinkSocial), whose README provides attribution and counts" [BK1:experiments/icsec_final/authoritative_run_v2/DATA_GOVERNANCE.md#L3]. The thesis revision cites `https://github.com/vishalshar/Dataset-LinkSocial` and notes that the public repository statistics differ from the project's prepared data [BK1:docs/report_revision/REFERENCE_CHECK_CHAPTERS_1_2.md#L18]. The paper cites `linkSocial2018` [BK1:paper/reviewer_revision/main.tex#L44]. The architecture doc lists `prepare | LinkSocial JSON` [BK1:docs/ARCHITECTURE_TH.md#L44].
3. **Raw data not present.** `data/data/Dataset-LinkSocial` is a gitlink (mode 160000) to commit `fe67dd1102d9265fb5c47d0f3d8ff19546294571`, with no `.gitmodules` and no content [BK1:data/data/Dataset-LinkSocial gitlink]; [BK1:docs/reports/ICSEC_REVIEW_REPO_AUDIT_TH.md#L100-L105]; [BK1:docs/research_rebuild/phase_01/05_DATA_AND_EXPERIMENT_LIMITATIONS.md#L7-L9]. A CSV copy `train_data/Project-for-Work/data/data/Dataset-LinkSocial/data/cleaned_social_data.csv` exists only as an LFS pointer [BK1:train_data/Project-for-Work/data/data/Dataset-LinkSocial/data/cleaned_social_data.csv lfs-oid:c930a8be4ace content-not-inspected].
4. **Explicit statement that labels are unverified annotation.** "Ground truth เป็น corpus annotation ไม่ใช่ identity verification ภายนอก": labels use the user_folder/numeric mapping of the derivative and cannot prove that the upstream collector grouped every person correctly [BK1:docs/research_rebuild/phase_01/05_DATA_AND_EXPERIMENT_LIMITATIONS.md#L11-L15].
5. **Consistency audits (internal only).** 15,297 known entity groups; user_folder↔numeric profile_id has no one-to-many conflict; 3 rows lack an entity [BK1:docs/research_rebuild/phase_01/01_DATASET_AND_FEATURE_LINEAGE.md#L100-L108]. The historical GT CSV has 6 directed pairs linking different index entities, 3 index/merged folder mismatches, and 29,246 vs canonical 29,243 cross-platform pairs. The NPZ matrix is missing [same#L106]; [BK1:docs/research_rebuild/phase_01/06_PHASE_1_READINESS_GATE.md#L17]. There are 121 rows with duplicate (platform,userName) [BK1:handoff/worktrees/research-phase15-integration/docs/research_rebuild/phase_01_5/GATE_STATUS_MATRIX.md#L8]. An ordered user_folder comparison between two normalized snapshots differs on 14,348 rows (schema/order difference, not reconciled) [BK1:docs/research_rebuild/phase_01/01_DATASET_AND_FEATURE_LINEAGE.md#L81].
6. **Gate status.** Gate 3 (Ground truth) is "NOT VERIFIED — No signed label provenance/assumptions decision" [BK1:…/phase_01_5/GATE_STATUS_MATRIX.md#L9]. The approval request asks the owner to "Identify label source/owner and authority, positive/negative definitions, adjudication method, known uncertainty" [BK1:handoff/worktrees/research-phase15-integration/docs/research_rebuild/phase_01_5/HUMAN_APPROVAL_REQUEST.md#L18-L22]. All record fields are blank [same#L53-L62].
7. **The only statement about how upstream grouped users is an unverified assertion in an AI-prompt file.** "`user_folder` ground truth comes from users who publicly cross-linked their accounts — argue why this creates CONFIRMATION BIAS…" [BK1:docs/prompts/prompt_library.md#L145-L149]; also "LinkSocial users cross-linked accounts publicly, but did they consent" [same#L445]. This is a prompt template written as a premise. It cites no source and is not a provenance record.

### Was blocking / URL evidence used to build the labels?
- **No project-side evidence that blocking or URL features built `user_folder`.** Labels come from the upstream folder name (item 1), and candidate generation is computed separately from labels [BK1:experiments/code/run_icsec_authoritative_v2.py#L83-L97,L100-L104].
- **The reverse dependency cannot be ruled out.** If upstream grouping relied on publicly declared cross-links (item 7, unverified), exact-URL/username matching and URL/domain features would partly recover the labelling mechanism. Circumstantial: exact-tier TP 12,340 / FP 63 (99.5% precision) [BK1:docs/research_rebuild/phase_01/01_DATASET_AND_FEATURE_LINEAGE.md#L130]. Test-role exact tier precision is 0.9975 / 0.9965 / 0.9997 [BK1:artifacts/audit/icsec_review_20261010/evidence.json#exact_test_metrics]. The repository contains no document stating how LinkSocial constructed its folders.

### G0 conclusion
**PARTIAL / NOT VERIFIED.** The mechanism (upstream directory name) and source attribution (LinkSocial, gitlink revision fe67dd11…) are evidenced. Who created the grouping, how, with what evidence (e.g. self-declared links), adjudication and error rate are **not documented anywhere** in either backup commit. No signed label-authority record exists.
