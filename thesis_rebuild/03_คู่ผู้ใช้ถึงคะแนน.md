# 03 — ขั้นตอน Machine Learning ทั้งหมดของเรา

อ่านไฟล์นี้เป็นเส้นทาง **จากข้อมูลดิบถึงคะแนนโมเดล** แล้วดูว่าคะแนนถูกนำไปใช้ต่ออย่างไร ยังไม่ต้องรันโค้ดใหม่

```text
ข้อมูลดิบ → ทำความสะอาด → สร้าง label/คู่ → แบ่ง entity → สร้าง features
→ เทียบโมเดล → จูนบน validation → train → calibration → เลือก threshold
→ test → ให้คะแนน candidate ทั้งระบบ → policy → รวม entity / วิเคราะห์ข้อผิดพลาด
```

## A. เตรียมข้อมูลและป้องกันข้อมูลรั่ว

| ขั้น | ทำอะไร | ได้อะไร / หลักฐาน |
|---|---|---|
| 1. Prepare | อ่านโปรไฟล์ Twitter, Google+, Instagram; จัดการข้อมูลขาดและ normalize ข้อความ | โปรไฟล์ที่สะอาด — [prepare.py](../src/identity_resolution/stages/prepare.py) |
| 2. Label + pairs | `user_folder` เดียวกันและคนละแพลตฟอร์มเป็นคู่บวก; คนละ entity เป็นคู่ลบแบบสุ่มหรือชื่อคล้าย (`hard negatives`) | ตัวอย่างมี label สำหรับฝึก — [pairs.py](../src/identity_resolution/stages/pairs.py) |
| 3. Entity-aware split | แบ่ง **คน** ก่อนใช้คู่ใน train/validation/test เพื่อไม่ให้คนเดียวกันข้ามชุด | split ที่ entity ไม่ทับกัน — [main_report.json](../pub_multi/ref/main_report.json) หัวข้อ `leakage_report` |
| 4. Feature engineering | วัดความคล้ายของชื่อ bio URL location metadata และหลักฐานภาพ รวมทั้งบอกเมื่อ field หาย | ตาราง feature หนึ่งแถวต่อคู่ — [features.py](../src/identity_resolution/stages/features.py) |

**แยกสองคำนี้:** *labeled pairs* เป็นตัวอย่างสำหรับฝึกและวัดโมเดล ส่วน *blocking candidates* คือคู่ที่ระบบเลือกมาให้คะแนนจากคู่ที่เป็นไปได้ทั้งหมด อ่านเรื่อง blocking ใน [ขั้น 02](02_ข้อมูลถึงคู่ผู้ใช้.md)

**ชื่อชุดข้อมูลที่เจอบ่อย:** `TRAIN` ใช้เรียนพารามิเตอร์โมเดล; `validation` ใช้เลือก config/threshold; `CALIBRATION` ใช้เรียนการแปลงคะแนน; `TEST` ใช้รายงานผลหลังเลือกทุกอย่างแล้ว สายระบบเดิมและ V2R1 แบ่งบทบาทไม่เหมือนกัน: V2R1 แยก `CALIBRATION` กับ `POLICY_VALIDATION` ชัดเจน จึงห้ามสมมติว่าไฟล์ทุกสายใช้ split แบบเดียวกัน

## B. ทดลองและเลือกโมเดล

| ขั้น | สิ่งที่ทำ | หลักฐาน |
|---|---|---|
| 5. เทียบชุด features | สาย multimodal เริ่ม text/attribute **23** ตัว → เพิ่มสถานะ/สถิติภาพเป็น **37** → เพิ่ม image-caption context เป็น **41** | [รายการ 41 features](../pub_multi/doc/feature_41_breakdown_th.md) |
| 6. เทียบ model families | งานพัฒนาหลายรอบลอง rule baseline, Logistic Regression, Gradient Boosting, Random Forest, Extra Trees, Linear SVM, AdaBoost และ MLP; ไม่เอาคะแนนจากคนละ protocol มาเรียงแข่งกัน | [model history](../pub_multi/doc/model_history.md), [model selection](../pub_multi/doc/model_selection_table.md) |
| 7. จูนการฝึก | ลองสัดส่วน random/hard negatives และค่าของโมเดล โดยใช้ validation เลือก | [tune.csv](../pub_multi/ref/tune.csv), [main run](../pub_multi/ref/main_report.json) |
| 8. Train final main run | ระบบเดิมเลือก Gradient Boosting + `image_context` **41 features**, run `image_context_r075_h20_s42` | [train_multimodal.py](../src/identity_resolution/stages/train_multimodal.py), [settings.py](../src/identity_resolution/settings.py) |
| 9. Calibration | หลัง train ใช้ isotonic calibration แปลง raw score เป็นคะแนนที่ policy ใช้ต่อ | [รายงานโครงการ](../manuscript/PROJECT_REPORT_TH.md) §7.2 |
| 10. เลือก binary threshold | สายประเมินโมเดลเลือก **0.35 จาก validation F1** โดยใช้ precision ตัดสินเมื่อเสมอ แล้วล็อกก่อน test | [evaluate.py](../src/identity_resolution/stages/evaluate.py) |
| 11. Test + error analysis | วัด AP, precision, recall, F1, FP/FN รวมทั้งแยกตามระดับความยากของชื่อและคู่แพลตฟอร์ม | [current_model_evaluation.json](../artifacts/evaluation/current_model_evaluation.json) |

ผลขั้น 11: supervised test **8,313 คู่**, precision **0.9507**, recall **0.9179**, F1 **0.9340** ที่ threshold 0.35 นี่เป็น **pair-model test** ไม่รวมคู่จริงที่ blocking ไม่เคยสร้างให้โมเดลเห็น

## D. งานทดลองแตกแขนงที่ทำแล้ว

งานเหล่านี้ **ไม่ใช่ 4 ขั้นที่ต้องรันเรียงกัน** แต่ตอบคำถามวิจัยต่างกัน:

- **N-series:** วิธีแทนความคล้ายของชื่อ — [รายงานโครงการ §11](../manuscript/PROJECT_REPORT_TH.md)
- **R0–R6:** representation, MiniLM, Bloom privacy, semantic blocking — [รายงาน R-series](../experiments/REPORT_R0_R5.md)
- **Feature-aware GA 10 พารามิเตอร์:** นโยบายอีกสายบน candidate population ที่ต่างกัน — [รายงาน full 2M](../artifacts/decisioning/feature_aware_ga/one_stage_weighted_full_2m_20260914/FULL_2M_ONE_STAGE_REPORT_TH.md)
- **GB-17/GB-18 + B0–B3:** การทดลองควบคุมในบทความล่าสุด ใช้ TRAIN / CALIBRATION / POLICY_VALIDATION / SEALED_TEST แยกกัน — [protocol V2R1](../experiments/icsec_final/authoritative_run_v2r1/PROTOCOL_V2R1.md)

`41 features / F1 0.9340` กับ `GB-17/GB-18 / B0–B3` ใช้ feature set, split และ metric ต่างกัน ให้เล่าเป็น **พัฒนาการระบบ** และ **ผลทดลองควบคุม** แยกกัน

**เช็กว่าพร้อมไปต่อ:** ลองเล่าว่า train, validation, calibration และ test ใช้ทำอะไร แล้วอธิบายว่าทำไม F1 ของโมเดลจึงไม่เท่ากับคุณภาพหลัง blocking + policy
